## 5G.1 fix-ups

| # | Item | Result |
|---|---|---|
| 1 | Portal session persistence | ✅ Backend: opt-in cookie mode (`X-Auth-Mode: cookie`, seller only) — refresh token is an **HttpOnly, Secure, SameSite=Lax cookie, `Path=/api/auth/refresh`**, optional `Domain` via `AUTH_COOKIE_DOMAIN`, rotated on **every** refresh, **reuse detection revokes the whole family** (401 `REFRESH_REUSE`; a simultaneous two-tab refresh gets a retryable `REFRESH_IN_PROGRESS` within a 10 s window instead of killing the session). **CSRF**: strict Origin/Referer check against `PORTAL_ORIGINS` (403 `CSRF_ORIGIN`) + double-submit token (`GET /api/auth/csrf`, `X-CSRF-Token`, 403 `CSRF_TOKEN`). `DELETE /api/auth/refresh` logs out; logout, password reset and deletion request revoke families. Access token stays in memory. Mobile body flow unchanged (regression-tested). Portal restores the session on load and after Stripe (reload stays signed in — **verified in a real browser against the real API**). Deploy notes (shared registrable domain, what breaks in Safari otherwise, how to verify) are in the portal `DEPLOY.md` and the runbook. |
| 2 | Apple accounts keyed by `sub` | ✅ New Apple users always get an account, including Hide My Email (relay email stored from the first authorization; if no email at all, a non-deliverable `apple+<sub>@apple-signin.invalid` placeholder flagged `emailIsPlaceholder`, never mailed). Later logins without an email resolve by `sub`. Linking to an existing password account only via a **verified** email match. Private-relay setup note (register the sending domain) in portal `DEPLOY.md` + runbook step 5. |
| 3 | Apple token revocation | ✅ Clients send `authorizationCode`; the backend exchanges it (ES256 client secret from `APPLE_PRIVATE_KEY/KEY_ID/TEAM_ID`) and stores Apple's refresh token **AES-256-GCM encrypted** (`APPLE_TOKEN_ENC_KEY`). **Revoked at purge** (the account is recoverable for 30 days; decision documented), failure never blocks deletion — recorded and retried with backoff (hourly, cap 24 h, 8 attempts, loud log after that). Tested with Apple's HTTP stubbed — **not against Apple** (blocker B2). |
| 4 | Stripe success page without a session | ✅ Public `GET /api/pos-checkout/session-status?sessionId=cs_…` → `{status, planActivated, storeId}` only (no amounts/emails; unknown/non-POS ids → `unknown`); the success URL carries `session_id={CHECKOUT_SESSION_ID}`; the page shows "payment received, plan activating" until the webhook lands, polls ~60 s. |

- **Local stack** (`solvexo-api/dev/`): `docker-compose.dev.yml` (Mongo replica set + Redis + API + seed) — **syntax-checked only, Docker is not installed here** — and an equivalent native stack (`npm run dev:stack:up/down`, own mongod `:27118` rs `rsdev`, redis `:6479`, API `:3102`; the user's own mongod/redis/`.env` untouched). Idempotent seed (`npm run dev:seed`): owner, "Dev Coffee" (USD, 10 % tax) with limited / unlimited / low-stock products, manager (PIN 1111) + cashier (2222), active POS plan, plus an expired-plan store; `dev:expire-plan` / `dev:restore-plan`; extra owners for the portal tests. OTP read hook = a dev-only mail sink to `dev/.logs/mail.log` (`DEV_OTP_LOG`, impossible when `NODE_ENV=production`, unit-tested); `DEV_DISABLE_THROTTLE` likewise. How to run: `dev/README.md`.
- **POS app on the iOS simulator vs the real API — 11/11 flows PASS** (re-run by me on the final code incl. the new offline receipt change; both files "All tests passed"): device setup; PIN login (wrong PIN, cashier, manager); sale with manager discount (server totals, stock decrement; cashier discount refused by the backend); split tender (card 20 + cash 15, change 5.85); partial refund (card first, then cash) and void (stock restored; cashier can't refund); **offline sale with the API really stopped → restart → sync → exactly one sale** with the original key and a real number; idempotent retry (same key twice → one sale); close shift (expected cash = opening + cash sales − cash refunds; variance 0, short count −2); plan expiry → restricted (sell/open refused, read/refund/close allowed) → restore; device revocation (credentials cleared, store binding and queue kept; re-register uploads the queued sale); account deletion from the app (throwaway owner; pending_deletion, devices revoked; cancelled afterwards). Plus a UI pass tapping the real screens through login → device setup → PIN → open-register. Re-run: `cd pos && tool/run_real_e2e.sh`. No iOS ATS change needed (Dart sockets), release config untouched.
- **Portal vs the real API — 18/18 Playwright tests PASS** (two runs by the workstream): password sign-in; **reload stays signed in** (incl. deep link); cookie attributes verified; no tokens in web storage; logout; rotation + **reuse detection**; CSRF (no origin, foreign origin, missing/forged token); stores/plan status; plans in currency; devices list + revoke (device token stops working); password deletion + cancel by signing in; public OTP deletion (generic message for unknown email, wrong code, reuse); public pages. **Found and fixed a real bug:** cookie-mode login was rejected because the portal didn't send the CSRF header on login; the mocked tests hadn't enforced it. Re-run: `cd solvexo-account-web && npm run e2e:real`.
- **Found by the real run, fixed in this phase:** the provisional **`OFF-<deviceShort>-<seq>` receipt number from decision Q7 had never been built** (offline-queued sales had no receipt at all). Now: per-device persisted monotonic sequence (deviceShort = last 6 chars of the id — the first chars are a creation timestamp), shown on screen/print/PDF/share with an "OFFLINE — PENDING SYNC" note, mapped to the real number after sync (kept as "Offline ref"), never sent to the server; DB migration v4; 20 tests. Rows queued before this change keep no provisional number.
- **Stripe real test-mode run — NOT run, by choice and by constraint.** The Stripe CLI is not installed, and the local stack runs `PAYMENT_PROVIDER=manual` (the API won't boot with a blank Stripe key). I also did not read your `.env` to check for test keys (that read is blocked in this environment) and used no keys. So checkout, early-renewal stacking, refund and dispute are covered only by real-Mongo tests with a stubbed Stripe client (billing suite incl. `charge.dispute.closed`). This is blocker **B1** in `go_no_go.md`, with the exact steps.

### B. Test gaps
`test_gap_matrix.md` maps all 30 audit gaps, Q1–Q14 and 17 residual risks to covering tests: 23 gaps already covered, 3 newly covered (#23, #27, #28), 3 not fully automatable (#12 Play SHA-1 console setting, #20 printer/drawer hardware, #29 accessibility), #30 is a process item.
