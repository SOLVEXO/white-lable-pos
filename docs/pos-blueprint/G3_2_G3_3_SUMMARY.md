## G3.2 — lot sale rules (D4)
* **FEFO at sale:** lot-tracked variants take units from lots — soonest expiry first, then no-expiry (oldest first); the sale line records `lots[]` (`lotId, lotNumber, qty, expired, costPriceMinor`); one stock-ledger row per lot. Concurrency-safe (conditional `$inc` per lot; 12 tills on 5 units → exactly 5 sales). Held-sale completion now also writes its ledger rows and takes lots (a G3.1 gap fixed).
* **Expired lots blocked:** expired units are not available (existing availability rule); a **manager-approved override** (`items[].sellExpired` + manager PIN, matrix action `inventory.lot.sellExpired`, "always needs a manager") sells good units first, then expired ones; audit `expired_lot_sold` names the lots and the approver. The service never trusts the flag without the controller's approval.
* **Returns / voids go back to the original lot** (cumulative mapping in the order sold; a depleted lot is active again; non-restocked lines touch no lot).
* **Transfer:** the FEFO suggestion endpoint (`GET pos/inventory/lots/:store/:variant?qty=`) is what a transfer will use; the transfer screens themselves are not part of this step.
* **Expiring soon:** Home dashboard `expiring {expiredLots, in7, in30}` (managers), stock-list filter `expiring`, rows carry `expiredUnits` / `nextExpiryAt`.
* **Offline — decision (documented):** the till shows the **last online FEFO preview** of the item ("as of <time>", persisted cache of 200); it **never blocks** an offline sale and never sends `sellExpired`. The server allocates at sync: expired lots are used only when nothing else covers the quantity and the sale is flagged `expired_lot_sold_offline`; units no lot can cover are flagged `lots_short`; both set `needsReview` → they appear in **Needs attention** (readable wording in the app). Replays of the same offline sale never take a lot twice.

## G3.3 — customers, loyalty, store credit (D2, D3)
* **Customers:** till directory (`PosCustomer`; phone unique per store = natural key; same phone returns the same person), add / edit / profile, search that also finds storefront buyers of the store; **D8 fields** (name, NTN, CNIC, address, registration type, group, notes, consent) all optional; edit is manager-only and audited with before/after; profile shows balances to every role and lifetime spend to managers only; credit ledger + manual credit adjust (manager; above the limit the **owner**).
* **Loyalty (D2), integers only:** earn = `floor(net spend / posEarnSpendMinor)` (after discount, before tax); redeem = points × `posRedeemMinorPerPoint` as a discount priced by the server, **online only**, not combined with a coupon / manual discount; the guarded take of points is in the sale transaction; **reversal on returns is proportional and cumulative** (any chunking reverses exactly what was earned — tested at exponent 0 / 2 / 3), redeemed points come back with the money; voids reverse everything; a held sale earns when completed. Owner sets the two rates (audited). Expiry stays the existing optional `pointsExpiryMonths` (off by default).
* **Store credit (D3):** new append-only minor-unit ledger + lots; **tender** (`store_credit` payment line, online only, needs a customer, spend inside the sale transaction) and **refund method** (`refundTo: store_credit`, above `storeCreditRefundMinor` a manager must approve; a sale paid with credit always returns to credit; credit note tender `store_credit`); shift totals count it with "other".
* **Option B + the owner's condition:** see `G3_STORE_CREDIT_LEDGER_PLAN.md` §5. The "storefront switch" is the **same service** switching storage (`STORE_CREDIT_LEDGER=legacy|migrating|new`), so the till and the storefront can never be on different ledgers; the till's tender is refused / hidden unless the mode is `new`; the storefront API (same methods, same response shapes) is unchanged — the legacy-vs-new contract scenario gives identical results in USD / JPY / KWD and the 249 existing storefront tests (orders, checkout, payment, refund-request, scheduler) pass unchanged. Dual spend: tested at every step (mode switch; 20 concurrent spends; storefront vs till racing 27 rounds; same checkout redeemed 6× at once). Migration: dry run + `up` + `down` on a copy of dev with synthetic rows → database hash identical after `down`; `down` refuses when the new ledger has rows of its own (dev seed) unless forced; runbook step 7.
