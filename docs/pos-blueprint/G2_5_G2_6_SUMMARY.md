Branch `feature/jamibranch` in both repos. No PRs, no merges, no deploys, no admin UI. Reports (Cloudinary, Stripe) and the FBR plan are separate documents: `CLOUDINARY_HELPERS_REPORT.md`, `STRIPE_REPORT.md`, `FBR_PLAN.md`.

## G2.4 follow-ups (decided by the owner)
* **A held sale keeps the coupon CODE** (not a reservation). The server stores `heldCouponCode`; nothing is discounted or counted while the sale is held (the till sends the total **without** the coupon). On resume the code is re-checked live (quote); if it is no longer valid it is removed and the cart says so with the reason **and the new total** (a banner with a dismiss, shown before charging). `completeSale` accepts a `couponCode` (validated live, usage counted inside the sale transaction; two-till race tested). Coupons stay **online-only**.
* **KYB PDFs**: `file_picker` added (approved), used by exactly one controller (a test pins that). The server validates **by content** (magic bytes): JPEG, PNG, PDF only — a renamed ZIP/HTML/text is refused whatever its name or Content-Type; the detected type is what is stored. Max size configurable (`KYB_MAX_FILE_BYTES`, default 10 MB). Same no-cache rules: the picked copy is deleted after upload.

## G2.5 — what was built
**Backend** (`pos-documents.util.ts`, `pos-credit-note.schema.ts`, `pos.service.ts`, `pos-receipt.service.ts`)
* **Tax-invoice number**: every completed sale gets `invoice.number` (`INV-000001`), per store, **gap-free**: the counter is incremented **inside the sale's transaction**, so a sale that fails leaves no hole; two tills contend on one counter document (8 concurrent sales → 1..8, tested). A held sale gets its number when it is completed. **Immutable**: a model hook refuses any update touching `invoice` except the one that first issues it; unique per store.
* **Credit note** for every return and every void: its own gap-free per-store number (`CN-000001`), linked to the original invoice and lines, reason, items, quantities, per-line tax reversed, restock flag per line, tenders refunded, who approved and why. **Append-only** collection (update/delete/replace refused). Corrections are new documents.
* **Transmittable shape** (FBR_PLAN §7/§8): seller snapshot (legal name, address, NTN, STRN), per-line net / tax / discount share, **PCT/HS code snapshotted on the sale line**, tax category, payment tenders, and placeholders `fiscal: {status:'not_enabled', externalInvoiceNumber:null, qrPayload:null, attempts:0}` on invoice and credit note. (Credit notes are immutable, so future transmission progress will be appended as events, not written into them.)
* **Per-line tax breakdown**: Σ lines = the sale's discount and tax exactly (largest-remainder). A return is priced by **cumulative proration** — credits of all returns of a line add up to exactly what it cost, in any order/chunking, for exponent 0 / 2 / 3 (tested JPY / USD / KWD). Discounts and **coupons** are shared out over the lines; an exempt custom item reverses no tax. Older sales (no invoice / no stored breakdown) keep working: the breakdown is derived, the credit note equals the amount paid out.
* **Partial return**: quantity per line ≤ sold − already returned, **race-safe** (optimistic claim on the sale; of two/three simultaneous returns exactly one wins; stock restored once); **restock per line** (yes/no — "no" needs a reason; a custom item is never restocked); a full refund now also counts each returned unit on its line (found by a CI run — see below).
* **Refund method**: the sale's own tenders in the documented order (card/other first, cash last); **cash refund needs an open shift** (`OPEN_SHIFT_REQUIRED`); Raast goes back through provider refund events; recorded-unverified card refunds are recorded the same way. **No store credit** (G3).
* **Manager approval**: per store (owner screen): `cashierReturnsEnabled` (default **off** = every return needs a manager, exactly as before), `returnApprovalAboveMinor`, `returnApprovalAfterDays`, and "no original receipt" always needs a manager. A cashier outside the limits gets `403 RETURN_NEEDS_MANAGER` with the **reasons**; a manager's PIN approves; the credit note records `approvedBy` + `approvalReasons`.
* **Public tax invoice + credit-note pages** behind the same unguessable receipt link: `/r/:token/invoice` and `/r/:token/credit-note/:number` (seller as registered, per-line tax, HS code, credit notes list; **no customer data**; same single 404 for unknown / malformed / revoked / other-sale). `GET pos/sales/:id/documents` for the till.
**App**: *Tax invoice* screen (number, seller as registered, lines with tax + HS code, totals, tenders, credit notes) with **Share PDF** and **Share link** (the `/invoice` page); *Credit note* screen (against which invoice, tax reversed, restocked or why not, approved-by) with PDF + link; **Return items** (lines + quantities, restock switch + reason, "customer has the original receipt", the credit estimate — the server's own proration — and how it will be paid back per tender) → manager sheet when the server asks → **Return recorded** (credit note number, what to hand over per tender, open the credit note). Entry: order detail → *Tax invoice* / *Return items*. Layouts leave a reserved band for the future FBR invoice number / QR / logo. Printing = the PDF share sheet (no printer driver added).

## G2.6 — what was built
* **Home dashboard** (`GET pos/dashboard/:storeId`, role-based **by the server**): today's sales, orders, average sale, refunds, top products, payment mix, low stock, needs attention (review + digital), open shift(s). A **cashier gets only their own open shift** and none of the store-wide parts (tested: no other cashier's name in the payload). Numbers come from the same `summarizeSales` as the daily report → **equal to the report to the minor unit** (tested on mixed sales incl. split tenders, refunds, a void). Efficiency: read through the (storeId, createdAt) index with a projection; a test asserts an IXSCAN and 600 sales answer in < 3 s.
* **POS catalog edits** (D3): `PATCH pos/catalog/:storeId/variants/:id` (price, barcode, PCT/HS code, category) and `POST …/stock` — **manager PIN** every time (a non-manager is asked for one on the spot), **audit before/after**, written to the same variant/product documents the storefront reads (verified through the public storefront route), barcode **unique per store** (409 `BARCODE_IN_USE`, legacy rows without `storeId` matched via their product), prices must be **exact in the currency's minor units** (`PRICE_PRECISION`), stock only through the **stock-movement** path (never an overwrite), category must be available to the store.
* **Store tax profile** (owner, behind the owner gate): NTN, STRN, registered name/address, default tax category (applies to a custom item that does not say) — optional now, snapshotted on every invoice/credit note — plus the return policy above.
* Found and fixed on the way: **`getProductByBarcode` was global** (two stores with the same barcode could not both scan); the POS product lists **did not carry `barcode`**, so the till's "local catalogue" scan lookup could never hit (they now carry `barcode` and `hsCode`).

## Offline invoices: how they get their final number (report)
An offline sale gets its **final invoice number when it syncs**, inside the server transaction, so the sequence stays gap-free and duplicate-free across tills. Numbers therefore follow **sync order**, not the order the sales were made; the invoice's **issue date keeps the device time** (`clientCreatedAt`). The provisional `OFF-…` number: the **till keeps the link on the device** (its receipt record holds provisional → real number and sale id, and a reprint shows both). The server invoice has an `offlineRef` field and accepts it, **but the app does not send it**: an earlier, tested rule says nothing of the OFF- number is part of what is sent to the server. **Decision for you**: send it (so the server-side invoice also names the paper copy), or keep it device-only. Note for FBR (FBR_PLAN §5): offline-mode invoices must be marked and uploaded within 24 h of restoration; invoice numbers that are not in time order may need a decision with FBR.
