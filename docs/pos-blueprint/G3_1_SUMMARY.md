# G3.0 (rest) + G3.1 — summary

Branch `feature/jamibranch` (both repos). No PRs, no merges, no deploys, no admin UI. Decisions D1–D6 as given; D7–D10 not built (§6).

## 1. What was built
**Permission matrix (D1, D6) — backend.** `src/pos/pos-permissions.config.ts`: ONE data table (action → roles → approval rule) + documented per-store limits; `PosAuthorizer` evaluates it (device + PIN session → cashier/manager, owner login → owner; manager-PIN approval via `x-pos-approver-token`; owner approval only from the owner's own login; every denial/approval audited). Routes name an action, they contain no role checks. Spec: **127 cases** — every action × every role, below and above each limit (allowed / denied / needs approval), inclusive limit, exponent scaling, overrides. Tables: `G3_PERMISSIONS_AND_LIMITS.md` (generated).
**Limits (D6):** `PosSettings.approvalLimits` (additive), read by managers, **edited by the owner only** (`PATCH pos/inventory/limits/:storeId`, audited before/after). Defaults documented (money = major units × currency exponent): a cashier may adjust stock alone up to 5 units / 20.00 at cost; cash-out and expenses 100.00; refund to store credit 50.00; supplier payment 500.00 manager / 2000.00 owner; store-credit adjust 100.00; loyalty adjust 500 points.
**Money twins** (purchase orders + lines, supplier returns + lines, lot costs, variant costs): dual-written at every write site (PO schema hook, PO receive, supplier returns, variant cost edit), consistency checker (logs + counts, never rejects), never exposed on public variants; backfill script `pos-g3-cost-minor-backfill` (dry run, idempotent, resumable, reversible, refuses non-dev). Tests: parity, off-grid reporting, JPY/USD exponents, byte-for-byte `down` (9). **Dev data has no POs/lots/costs** (4 variants, none with cost), so the dev dry run reported 0 candidates — the proof is the spec, not dev data.
**Stock ledger (D5, memo `G3_STOCK_MOVEMENT_MEMO.md`):** new append-only `StockMovement`; sale / return / void rows inside the document's transaction; every `StockAdjustment` (manual, PO receipt, supplier return, write-off, expiry, count) writes its row in its own session; **unit cost snapshot (weighted average) on every sale line and every row**; reconciliation `opening + Σ qtyDelta = stock` asserted; no history backfill.
**Till-facing inventory routes (G3.1):** `pos/inventory/` overview, stock list, low stock, lookup by barcode, variant detail, movements (managers), adjust, counts (start/list/get/find-by-scan/enter/finish/cancel), approval limits. Cost/value/history are manager/owner only. Reads stay available on a lapsed plan; writes need the plan. 16 integration tests (`pos.g31`).
**App (G3.1, built by a sub-agent, reviewed):** overview, stock list, item detail (locations, lots with expiry badges, recent movements), adjust sheet with the manager-PIN approval retry, movement history, low stock, **stock count with scan** (camera scanner or typed code → find → quantity → variance review → finish), approval limits (read-only); More-hub entries (managers: Inventory; cashiers: Stock). Tests +103 (31 controller, 60 widget runs = 20 screens × phone/tablet/dark, 12 repository). **Real-backend iPhone-simulator flow passed** (sale → stock + ledger row → cashier adjusts −2 alone → −9 asks approval → real manager sheet → success → count by barcode → variance → finish → stock = counted; cashier gets 403 on history and on starting a count). 26 + 26 screenshots (phone / tablet × light / dark) in `g3_1_screenshots/`.
**Backend finding fixed:** a count's variance was recorded as type `adjustment`; it is now type `count` (spec updated).
